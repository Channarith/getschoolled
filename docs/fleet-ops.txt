FLEET OPS: RUNNING TRAINING, TRANSLATION AND VOICE WORK ON THREE MACHINES
=========================================================================
Plain text on purpose (repo no-markdown house rule).

Goal: use the Mac, the iBuyPower (Kal-el) and the DGX Spark together to build the Salareen
education model and voice agent, without any one machine running out of memory, CPU or GPU, and
without leaving dead or runaway processes behind.

WHO RUNS WHAT
  DGX Spark (Chans-Spark, nvidia@192.168.1.107, GB10, 121 GB unified memory)
    Main trainer. LLM QLoRA (training/spark_nightly.sh), evaluation and bake-off, and one TTS
    fine-tune at a time. Reserve: 16 GB RAM and 2 cores stay free.
  iBuyPower (Kal-el, cvanthin@192.168.1.118, RTX 5060 Ti 8 GB, 30 GB RAM)
    Data and inference. NLLB course translation, ASR / transcription, audio denoising, dataset
    preparation and conversion, TTS inference for the voice bake-off. NOT for large training: 8 GB
    of video memory fits small models only. Reserve: 6 GB RAM and 2 cores stay free.
    Its address comes from DHCP and has moved .113 -> .117 -> .118. Fix it with a DHCP reservation
    in the router; until then use FLEET_HOST_KALEL=<ip> or the Kal-el.local name (fallback is automatic).
  Mac (coordinator)
    Repo and git, scoring and validation (data checks, benchmark scoring, ASR round-trip error),
    staff review work, MLX experiments on small models. No long GPU jobs. Reserve: 8 GB RAM, 2 cores.

THE RULES
  1. One GPU job per machine at a time. gs_run.sh --gpu takes ~/.gs-gpu.lock (the same lock
     training/spark_nightly.sh uses) and the second job waits or is refused.
  2. Every long job starts through scripts/gs_run.sh. No bare "python3 ... &", no nohup, no
     terminals left running servers. gs_run sets memory, CPU, IO and task limits, refuses to start
     when free memory is under the reserve, and kills the WHOLE job (every child) when it stops,
     times out, or you press Ctrl-C. That is what prevents orphans and zombies.
  3. Always give long jobs --timeout. A job with no timeout is a runaway waiting to happen.
  4. Do not run two jobs against the same output folder (the translation batches split languages
     between machines for that reason: docs/translation-run.txt).
  5. Look before you start: scripts/fleet_status.sh. Clean up with scripts/fleet_reap.sh.
  6. Data moves between machines with rsync -a (checksummed, resumable), and each dataset has one
     owner machine. The Mac holds the validated copy.
  7. Never use or store ssh passwords. Key login only (ssh-copy-id once per machine).
  8. A busy process is not a dead process. Several sessions (people, Cursor, Claude) work on these
     machines at once, in tmux sessions and git worktrees. Before stopping anything, read its owner
     in the status report (see OWNER ATTRIBUTION). Never stop a process you did not start.

COMMANDS

  See all three machines (read-only, one screen, exit 2 if anything is critical):
    scripts/fleet_status.sh
    scripts/fleet_status.sh --host spark
    scripts/fleet_status.sh --local
    FLEET_HOST_KALEL=192.168.1.119 scripts/fleet_status.sh       (address moved)
  Hosts are in scripts/fleet/hosts.conf. Limits are in scripts/fleet/budgets.conf.

  Start a job (from the repo root ON the machine that runs it):
    scripts/gs_run.sh --dry-run -- <command>                      shows limits, changes nothing
    scripts/gs_run.sh --name NAME --timeout SECONDS -- <command>
    scripts/gs_run.sh --gpu --name NAME --timeout SECONDS -- <command>
  Useful options: --min-free-gb, --mem-max GB, --cpus N, --nice N, --gpu-lock-timeout S.
  Exit 75 means "not enough free memory" or "GPU lock busy": wait, do not force it.
  Job records live in ~/.gs-jobs/<id>.json (state: running, finished, failed, timeout, killed, lost).

  Clean up (dry run unless --yes; it only touches gs_run jobs, dead job records, a stale lock note,
  and PIDs you name):
    scripts/fleet_reap.sh
    scripts/fleet_reap.sh --yes
    scripts/fleet_reap.sh --zombie-parents --yes     also TERM the parent of any zombie
    scripts/fleet_reap.sh --pid 1234 --yes           stop one named process
    scripts/fleet_reap.sh --pid 1234 --i-know-owner --yes    ...even if it belongs to a tmux session
                                                             or worktree you did not start (see below)
    ssh -t spark 'cd ~/code/getschoolled && scripts/fleet_reap.sh'
  Owner protection: fleet_reap refuses any process that runs in a tmux session (it or a parent is a
  tmux pane shell) or whose working directory is in a linked git worktree, unless it was started
  through gs_run. This holds for every scope: --zombie-parents and runaway handling never override
  it. The only override is the explicit PID plus --i-know-owner, and the refusal message names the
  tmux session or worktree to ask first.
  A zombie cannot be killed: it is a finished process whose parent has not collected it. The fix is
  to make the parent exit or reap it, which is why fleet_status shows the parent next to each zombie.

  Per machine, one time:
    cd ~/code/getschoolled && git pull --ff-only
    scripts/fleet/install-units.sh --enable        installs gs-batch.slice, gs-job@.service and the
                                                   10-minute health check timer (user units, no root)
    scripts/fleet_status.sh --local

  Spark examples:
    scripts/gs_run.sh --gpu --name qlora --timeout 28800 -- training/spark_nightly.sh
    scripts/gs_run.sh --name cosyvoice-ingest --timeout 86400 -- python3 scripts/cosyvoice_batch_ingest.py --pool km,zh --workers 1
  (gs_run --gpu sets GS_GPU_LOCK_HELD=1 so spark_nightly.sh does not wait on a lock gs_run holds.)

  iBuyPower examples:
    scripts/gs_run.sh --name nllb --timeout 43200 -- scripts/translate_on_machine.sh run ibuy
    scripts/gs_run.sh --gpu --name tts-bakeoff --timeout 7200 -- python3 <bakeoff script>

  Mac examples:
    scripts/gs_run.sh --name score --timeout 3600 -- python3 training/evaluate.py ...
  (On macOS gs_run uses nice, caffeinate and its own process group; it cannot cap memory the way
  systemd can, so it relies on the free-memory floor and --timeout.)

HOW TO ADD A JOB
  1. Decide the machine from WHO RUNS WHAT above. GPU work: Spark first, iBuyPower for inference.
  2. Try it: scripts/gs_run.sh --dry-run ... and read the limits.
  3. Run it with --timeout (and --gpu if it uses the GPU).
  4. Recurring or reboot-proof: copy scripts/fleet/systemd/example.env to ~/.config/gs/<job>.env,
     edit GS_ARGS and GS_CMD, then: systemctl --user start gs-job@<job>
     Restarts are limited to 3 per hour and exit 75 is never restarted automatically, so a busy or
     full machine cannot cause a restart storm. WatchdogSec is not used: it needs a service that
     sends keep-alive pings, and batch scripts do not; the --timeout and the health check cover it.
  5. Check: scripts/fleet_status.sh --host <machine>, and journalctl --user -u gs-fleet-check.

OWNER ATTRIBUTION (who is this process, and is it working?)
  For every busy process (top CPU, top memory, orphans, parents of zombies) the status report shows:
    tmux session and window   found by walking the parent chain to a tmux pane shell
                              (tmux list-panes -a: pane pid -> session, window)
    working directory         and, inside a git repo, the worktree name, branch and last commit
    systemd unit or scope     from /proc/PID/cgroup
    parent chain              pid:command from the process up to init
    listening ports           and how many ESTABLISHED clients are connected to them (ss -tanp)
    last log write            age of the newest regular file on stdout or stderr
    device environment        NLLB_DEVICE, CUDA_VISIBLE_DEVICES, NVIDIA_VISIBLE_DEVICES only
                              (an allow-list; the full environment is never printed)
  The probe can only see what the logged-in user can see. Other users' processes show no cwd,
  environment or IO counters, and the report says "unreadable" instead of guessing.

  Working or spinning: ps %CPU is an average over the whole life of the process, so it cannot tell
  a busy server from a stuck loop. The probe reads CPU ticks and read+write bytes twice, 10 seconds
  apart (/proc/PID/stat and /proc/PID/io; --sample N changes the gap, --sample 0 skips it). For a
  process above 300% average CPU for 30+ minutes:
    busy-serving      (info)  clients connected, OR a log write in the last 5 minutes, OR more than
                              256 KB read or written during the sample. Never a kill suggestion.
    possible runaway  (warn)  still above 100% CPU during the sample, with no clients, no log
                              write and no IO growth. The suggested step is to ask the owner first.
    high CPU, unverified (warn)  no sample, unreadable IO counters, or CPU has calmed down since.
                              No kill suggestion either: the report cannot tell.
  Real example (2026-10-24): a uvicorn speech_gw at 760% CPU for 37 hours looked like a runaway. It
  was the NLLB translation gateway (NLLB_DEVICE=cpu) in tmux session nllb-speech, run from the
  worktree gs-wt/spark-eval-gates, with the course-translate session as its client. It was doing
  real work and was stopped before its owner was known. These rules exist so that cannot happen again.

WHAT THE STATUS REPORT FLAGS
  CRIT  unreachable host; memory under half the reserve; load over 3x cores; disk 95% full.
  WARN  memory under the reserve; load over 1.5x cores (3x is CRIT); possible runaway or unverified high CPU (above);
        zombies (with their parent and the parent's owner); heavy long-running jobs whose parent is
        init (unmanaged: start them through gs_run); more GPU processes than the budget; a stale GPU
        lock owner; a job record that says running but whose process is gone; CosyVoice ingest
        out-of-memory errors; GPU idle while 4 or more cores are busy (below).
  info  busy-serving processes; the top 3 processes with owner, chain, port and environment; unified
        GPU memory not reported (GB10 shows N/A: watch system memory); finished batch logs; running
        gs_run jobs; timers.

  GPU idle while CPU bound: "GPU 0% while N cores busy: check NLLB_DEVICE/CUDA device settings in the
  process environment", followed by the values read from each heavy process. NLLB_DEVICE=cpu or an
  empty CUDA_VISIBLE_DEVICES keeps a job off the GPU on purpose; if that was not intended, restart the
  job through gs_run with the device unset or cuda. The report cannot read another user's
  environment and says so.

KNOWN SPARK CLEANUP ITEMS (as of 2026-10-24)
  - The NLLB translation gateway (uvicorn speech_gw.main:app on 127.0.0.1:8002, NLLB_DEVICE=cpu, tmux
    sessions nllb-speech, nllb-gateway and course-translate, worktree gs-wt/spark-eval-gates) used
    about 7.6 cores for 37 hours. It was legitimate work, not a runaway, and it competes with the
    CosyVoice ingest for CPU while the GPU stays idle. The fix is not to kill it: ask its owner to run
    it on the GPU (NLLB_DEVICE unset or cuda) and start it through gs_run with a CPU quota.
  - A llama-server (Qwen 35B, snap qwen3-6) holds about 28 GB and was idle. If nothing needs it:
    sudo snap stop qwen3-6
  - The CosyVoice ingest (scripts/cosyvoice_batch_ingest.py, run by output/run_voice_queues.sh and a
    guard that relaunches it) should run under gs_run with a memory cap so an out-of-memory retry
    cannot take the machine down.

LIMITS THIS TOOLING CANNOT COVER
  - It reads and reports; it never stops anything on its own. Every fix is a suggested command.
  - Owner detection covers tmux and git worktrees. A process started from a plain ssh shell, a
    desktop terminal or a Cursor/Claude session without tmux shows only its parent chain and cwd,
    so "unknown" there means ask before stopping, not "safe to stop".
  - "Last request seen" is approximated by the last log write; ss does not carry request times.
  - Socket and client counts use ss and need Linux; on macOS the report shows no listening ports.
  - Memory caps use systemd on Linux. They need cgroup v2 controller delegation to the user manager
    (default on Ubuntu 24.04 and DGX OS); gs_run falls back to a process group and the free-memory
    floor if systemd-run is not usable.
  - The GB10 reports no GPU memory figure (unified memory), so GPU contention is judged by the number
    of GPU processes, not by video memory.

CUDA POLICY (DGX Spark)
  Rule: on the Spark all GPU work uses CUDA and nothing is pinned to the CPU. The single place that decides
  is aoep_shared/devices.py (pick_device). Components call it instead of testing torch.cuda themselves:
  NLLB translation, the CosyVoice ingest ASR (Whisper large-v3, MMS Khmer, language detection), fine-tune
  and evaluate in training/, and the Khmer eval script.

  Host role: AOEP_HOST_ROLE=spark|kalel|mac|other, else ~/.config/aoep/host.env (KEY=VALUE lines), else the
  hostname (contains "spark" -> spark, "kal-el" -> kalel). AOEP_REQUIRE_CUDA=1|0 overrides the role default.
    spark        CUDA required. No CUDA, no kernels for this GPU, or no PyTorch: the job stops at start with
                 the torch version, CUDA build, capability and arch list in the message. A CPU request
                 (NLLB_DEVICE=cpu, AOEP_ASR_DEVICE=cpu, --device cpu, CUDA_VISIBLE_DEVICES empty) is ignored
                 with a warning unless AOEP_ALLOW_CPU=1 is also set (use it only on purpose).
    kalel        CUDA preferred, CPU allowed with a warning (RTX 5060 Ti, 8 GB: one GPU job at a time).
    mac / other  MPS or CPU is fine.
  A startup smoke check runs real kernels (matmul and an fp16 Linear) so a PyTorch build without kernels for
  the GB10 (sm_121) is caught immediately, not hours into a batch.

  One-time setup on the Spark:
    mkdir -p ~/.config/aoep && printf 'AOEP_HOST_ROLE=spark\n' > ~/.config/aoep/host.env

  Why this exists: the Spark's NLLB gateway ran with NLLB_DEVICE=cpu for 39 hours (about 660% CPU, GPU at
  0%), and the CosyVoice ingest defaulted AOEP_ASR_DEVICE to "cpu", so Whisper large-v3 ran on the CPU.

  Check a machine (read-only; flags CPU pins and "GPU idle while CPU-bound"):
    scripts/fleet_cuda_check.sh                        this machine
    scripts/fleet_cuda_check.sh nvidia@192.168.1.107   the Spark over ssh (key login)
  The translation gateway answers GET http://127.0.0.1:8002/device with the device in use, whether CUDA is
  required, free GPU memory and ok true/false (503 when the policy is violated).

CONTINUOUS OPERATION (the queue layer)
  The tools above are the safety net. docs/ops-schedule.txt describes the layer that keeps all three
  machines busy: scripts/gs_worker.sh (worker + queue commands), scripts/fleet/jobs/*.json (job types),
  systemd units gs-worker / gs-worker-revive / gs-queue-daily, scripts/fleet/daily_report.sh, and the
  queue findings in fleet_status (WORKER_DOWN, QUEUE_STALE_LEASE, CUDA_BLOCKED, IDLE_WITH_WORK,
  QUEUE_DEAD_JOBS, QUEUE_SUMMARY). Start long jobs through the queue, not by hand.

SPARK SERVICES UNDER VERSION CONTROL (scripts/fleet/spark-units/)
  The Spark's training loops were hand-made systemd USER services that lived only on that machine (a Cursor
  session created them). They are now in the repo so changes are reviewed, tested and reversible:
    aoep-llm-train        STEM QLoRA loop (llm-forever.sh); pause with the hold file ~/.gs-hold/stem-train
    aoep-voice-train      Khmer CosyVoice fine-tune loop (voice-forever.sh); held by ~/.local/share/aoep-train/hold-voice-train
    aoep-voice-ingest     CosyVoice data ingest (voice-ingest-forever.sh); GPU ASR only when the CUDA policy passes
    aoep-gpu-balance      memory/GPU monitor (aoep_shared/spark_balance.py); pauses yt-dlp and, only when justified,
                          stops the bake-off client
    aoep-course-translate LEGACY v1 CPU translation. Retired (replaced by scripts/translate_catalog_v2.py); the script
                          refuses to run unless AOEP_LEGACY_TRANSLATE=1 and the unit is only installed with
                          --with-legacy-translate.
  Full details, thresholds and the llama-server sleep setting are in scripts/fleet/spark-units/README.txt.

  What the monitor got wrong (and what it does now)
    1. It called ANY non-llama GPU process over 2 GiB "training", so evaluate.py (an evaluation) made it kill the
       bake-off. Processes are now classified by command line: fine-tune, evaluation, bake-off client.
    2. The llama-server runs with --sleep-idle-seconds 600: after 10 idle minutes it unloads its ~20 GB model and
       reloads it on the next request. The bake-off client was that request, and the monitor measured its decode
       rate over the first 60 seconds, which is the reload. Result: "decoded_gain=7..18 in 62s" and the client was
       killed at every cycle, so the bake-off that gates promotion never finished. Now nothing is measured until
       the server answers /health 200 and /slots, no kill is allowed for 600 s after a wake, and the rate window
       starts at the first decoded token and runs 180 s.
    3. It killed with 70 GB free. Now a starved bake-off is stopped only during a FINE-TUNE, only below a memory
       floor (24 GB), and during an evaluation only under 6 GB (an emergency).
    4. spark_nightly.sh now sends one tiny request to the llama-server before the bake-off stage
       (scripts/fleet/spark-units/llama-warm.sh), so the reload is paid up front. Best effort: it never blocks a cycle.

  Applying it on the Spark (never switch the main checkout: it is on a feature branch with jobs running)
    1. A clean worktree of main, and a stable name to point the units at:
         cd ~/code/getschoolled && git fetch -q origin
         git worktree add -f ~/code/gs-wt/main-$(date +%Y%m%d) origin/main
         ln -sfn ~/code/gs-wt/main-$(date +%Y%m%d) ~/code/gs-wt/main-current
    2. See exactly what would change (dry run, writes nothing; shows a diff against each live unit):
         ~/code/gs-wt/main-current/scripts/fleet/spark-units/install.sh --root ~/code/gs-wt/main-current
       Compare one unit by hand if you like:
         diff -u ~/.config/systemd/user/aoep-gpu-balance.service \
           <(sed "s#@ROOT@#$HOME/code/gs-wt/main-current#g" ~/code/gs-wt/main-current/scripts/fleet/spark-units/units/aoep-gpu-balance.service)
    3. Write the units (backs the live ones up first; restarts nothing, enables nothing):
         ~/code/gs-wt/main-current/scripts/fleet/spark-units/install.sh --root ~/code/gs-wt/main-current --apply
    4. Restart the monitor first: it only watches, and its exit handler resumes anything it stopped:
         systemctl --user restart aoep-gpu-balance.service
         tail -f ~/.local/share/aoep-train/balance.jsonl      (one JSON object per line, rotated)
         cat ~/.local/share/aoep-train/balance.status.json
    5. The others pick up the new definition when YOU restart them, at a moment you choose:
         systemctl --user restart aoep-voice-ingest.service   (abandons the channel being ingested; the queue resumes)
         systemctl --user restart aoep-llm-train.service      (stops the cycle that is running; a frozen loop is released)
    Rollback: the installer prints the exact command and the backup folder (~/.local/share/aoep-train/backup-<time>/).
    Overrides without editing a unit: put VAR=value lines in ~/.config/aoep/spark-units.env (read by every unit).
