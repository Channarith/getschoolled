SALAREEN EDUCATION MODEL - AUTOMATED TRAINING ON THE DGX SPARK / IBUYPOWER
==========================================================================
Plain text on purpose (repo no-markdown house rule).

Goal: start from the best open-weight base we can run, fine-tune it on clean
education data, and promote a new model only when it beats the current one on a
frozen benchmark WITHOUT getting worse at tutoring behaviour. We fine-tune, we do
not train from scratch: that needs far more compute than these machines have.

  training/data/eval_frozen.jsonl        200 items, UNCHANGED. recall (100) and
                                         abstain (100). Scored with token F1; the
                                         recall/abstain tags also feed the behaviour
                                         scorers (grounded / abstain accuracy).
  training/data/eval_behavior_v1.jsonl   136 items: hint ladder (hidden answer must
                                         not leak), spoken voice answers (short, no
                                         lists), refusals of unsafe or off-topic
                                         requests, and grounded answers.
  training/data/eval_multilingual_v1.jsonl  Khmer, Spanish, Vietnamese, Thai, Swahili,
                                         Bengali, Chinese. References are machine

                                         staff-reviewed gold pairs replace them:

                                           --gold-jsonl <export from the review lab>

  Never regenerate eval_frozen.jsonl except on purpose (build_eval_set.py).

  REFUSAL_MARKERS in training/scoring.py before trusting those language scores.

HOW A CANDIDATE IS JUDGED (promotion gate)
  1. Highest frozen F1 among models whose fairness gap is <= 0.1.
  2. And it must not regress on behaviour: abstain, refuse and hint accuracy must each
     be >= the base model's (training/nightly_candidates.py sets the floors from the
     base run). A model that wins F1 by guessing, or by giving away answers, loses.

TUTOR BEHAVIOURS WE TRAIN (training/tutor_format.py, tutor_sessions.py)
  hint     Socratic ladder: step 1 nudge, step 2 narrow, step 3 reveal with the reason.
  grounded answer only from the passage; abstain when it is not covered.
  voice    at most two short spoken sentences, no lists or symbols (voice agent).
  refuse   decline unsafe or off-topic requests kindly and offer a learning alternative.
  The reply language is the learner's language. The app (or system prompt) puts one mode
  line at the top of the student message; training and evaluation use the same strings.
  Data limits to know: hint ladders and the voice/grounded sessions are English; abstain
  and refusal replies exist in en/es/vi/zh only (their phrases are reviewed). Add more
  languages only after a native speaker approves the wording.

DATA-QUALITY GATE (training/quality_gate.py; runs before every export)
  Each session needs source and consent. Authored lessons use source authored:* and
  consent authored; class data needs opt-in (children: guardian-opt-in). It checks the
  language tag, removes exact/near duplicate questions, scrubs personal data (emails,
  phones, SSN, card numbers, secret links, passwords) or drops the session, and FAILS the
  run (exit 3) if race or ethnicity appears anywhere. Report: output/spark/data/quality.json.

RESOURCE RULES (nothing may starve a machine, nothing may be left running)
  Every long stage runs through training/lib_limits.sh: a RAM ceiling and CPU quota
  (systemd scope when available, else a plain process group), a timeout, a free-RAM
  watchdog that stops the stage when free memory drops under 6 GB (Spark) / 3 GB
  (iBuyPower), and its own process group killed on timeout, Ctrl-C or abort. The cycle
  refuses to start if free RAM is below reserve + 24 GB. Exit 75 means "not started or
  aborted to protect the host", never a crash. No zombies: children are always waited for.
  scripts/gs_run.sh (the fleet runner, docs/fleet-ops.txt) is used when present, so every stage also
  shows up in scripts/fleet_status.sh. Look at all three machines first: scripts/fleet_status.sh.

ORDER OF OPERATIONS ON THE SPARK (run in this order; do not skip ahead)
  Step 0. Look first (read-only), and find out what is ALREADY running.
    ssh nvidia@192.168.1.107
    free -g | head -2 ; uptime
    tmux ls                                   (sessions on 2026-10-24: course-translate, nllb-gateway, nllb-speech)
    ps -eo pid,ppid,etime,pcpu,args --sort=-pcpu | head -10 | cut -c1-200
    nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv,noheader
    nvidia-smi --query-compute-apps=pid,used_memory --format=csv,noheader
    scripts/fleet_status.sh --local           (shows the tmux session and worktree that own each process)
    Several sessions share this machine (the STEM nightly, the 222-course translation, the NLLB gateway,
    the CosyVoice ingest, a 35B llama-server). Do not start a second GPU job on top of a running one and
    do not kill anything you did not start. A process at high CPU is NOT automatically a runaway: on
    2026-10-24 the 660% python on port 8002 was the NLLB translation gateway doing real work for the
    course-translate job (it runs with NLLB_DEVICE=cpu; see docs/translation-run.txt for the CUDA change).
    Find the owner first (tmux session, worktree, listening clients), then ask them.

  Step 1. Get current code WITHOUT disturbing running jobs.
    The Spark main checkout (~/code/getschoolled) sits on a feature branch (cursor/voice-oom-limits-f3a6)
    that has diverged from main, and jobs run from it. Do NOT run git pull, git checkout or git reset
    there: switching branches under a running Python job mixes old and new code in its lazy imports.
    Use a separate worktree of main instead and run everything from it:
      cd ~/code/getschoolled
      git fetch origin
      git worktree add ~/code/gs-wt/main-$(date +%Y%m%d) origin/main
      cd ~/code/gs-wt/main-$(date +%Y%m%d) && cat VERSION
    Reuse the existing virtualenv from there (it holds the working CUDA torch):
      export PY=$HOME/code/getschoolled/.venv/bin/python
      export PYTHONPATH=$PWD:$PWD/packages/shared/src
    Untracked files in the main checkout (docs/frontier-readiness.html, docs/status/) stay where they are.
    Move the main checkout onto main only in a quiet window, after every job started from it has finished
    and been restarted through scripts/gs_run.sh.

  Step 2. Free memory and compute (only what is idle, and only after checking).
    The 35B llama-server is a root snap (qwen3-6) that holds about 28 GB. It showed 680% CPU on
    2026-10-24 while something used it, so DO NOT stop it until you know it is idle:
      ss -tnp 2>/dev/null | grep -E ":8342|:8080|llama"        (any ESTABLISHED client means it is in use)
      top -bn1 -o %CPU | head -12 | tail -6                      (idle means near 0% CPU)
    Only if there are no clients and CPU is near zero:  sudo snap stop qwen3-6   (undo: sudo snap start qwen3-6)
    The ingest job is dataset building for CosyVoice, not training. To cap it, restart it through the wrapper:
      scripts/gs_run.sh --name cosyvoice-ingest --mem-max 40 --cpus 6 -- <ingest command>      (it resumes per channel)
    Never move running processes by hand. Zombies cannot be killed: find and restart the parent.
      ps -eo pid,ppid,stat,cmd | awk '$3 ~ /Z/'
    Expect after this: at least 80 GB available and a load average that is falling.

  Step 3. Python environment (never use requirements.txt on the Spark).
    .venv/bin/pip install -r training/requirements-spark.txt
    .venv/bin/python -c "import torch;print(torch.__version__, torch.cuda.is_available())"
    Must print 2.14.1+cu130 True. If torch changed, STOP: pip replaced it; reinstall the cu130 build.
    Optional 4-bit: .venv/bin/pip install bitsandbytes   (if it fails, training uses bf16 LoRA).

  Step 4. Download candidate bases on a machine WITH network, then copy (the nightly runs offline).
    .venv/bin/python training/compare_bases.py --list --machine spark      (shows what fits)
    huggingface-cli download Qwen/Qwen2.5-7B-Instruct --local-dir models/weights/qwen2.5-7b-instruct
    Repeat for the ones you want to score (check each model card licence and id first):
      Qwen/Qwen3-8B  Qwen/Qwen3-14B  google/gemma-3-12b-it  meta-llama/Llama-3.1-8B-Instruct
    Space: about 16 GB per 8B model in bf16. Spark disk has 2.6 TB free.

  Step 5. Validate everything without a GPU.
    CHECK_ONLY=1 ./training/train.sh
    Expect the last line: ==> CHECK_ONLY ok   (seeds, tutor sessions, quality gate, export, config)
    cd training && ../.venv/bin/python -m pytest tests -q     (all pass)

  Step 6. Base-model bake-off (one command, one leaderboard).
    .venv/bin/python training/compare_bases.py --machine spark
    About 10-25 minutes per 7B-14B model. Output: output/spark/eval/bases/leaderboard.txt
    Read it: highest SCORE with abstain and refuse above the floors, and decent Khmer/Thai/
    Vietnamese/Swahili/Bengali rows (by_language_f1 in leaderboard.json). Weigh multilingual
    strength over general fame. Set the winner:
      export BASE_MODEL=$PWD/models/weights/<winner>
      and base_model in training/config/finetune.spark.yaml
    Also score Grok through its API on the same files as a cloud ceiling (optional).

  Step 7. ONE manual full cycle (do not arm anything new yet).
    First look at what is already running (Step 0). The nightly may already be running on this machine
    under another mechanism (a tmux loop or hold files); two GPU jobs must never overlap. The nightly
    takes the GPU lock itself (~/.gs-gpu.lock) and exits 75 if it cannot start safely.
    BASE_MODEL=$PWD/models/weights/<winner> ./training/spark_nightly.sh
    Expected stages: 1 seed + tutor sessions, 2 quality gate, 3 export, 4 train, 5 evaluate base and
    adapter on five benchmarks (split, frozen, STEM frozen, behaviour, multilingual), 6 bake-off, then the
    promotion gates. About 1,300 train examples: 4 train takes roughly 20-60 minutes on the Spark for a 7B,
    evaluation 15-40 minutes each (estimates, not measured: record the real train_seconds).
    Watch memory in another terminal:  watch -n 10 "free -g | head -2; nvidia-smi --query-gpu=utilization.gpu --format=csv,noheader"
    PROMOTION NEEDS ALL OF THESE (one gate, three conditions):
      a) the adapter wins the bake-off: fairness gap within the limit, weakest sampled subject at or above
         MIN_SUBJECT_SCORE (default 0.40), and abstain/refuse/hint accuracy not below the base model;
      b) its frozen-exam score is strictly higher than the last promoted score (promoted_frozen.json);
      c) no sampled subject on the frozen, STEM-frozen or split exams is under MIN_SUBJECT_SCORE.
    Anything else keeps it as a candidate (candidate.json). A repeated win over the base by an unchanged
    adapter is not progress. Outputs: output/spark/eval/<base|stem>/*.json plus the flat names the readiness
    briefing reads (stem.frozen.json, stem.stemfrozen.json, base.frozen.json), truth_curve.jsonl, bakeoff/*.
    If the cycle exits 75 it was not started or was stopped to protect the host; free memory and retry.

  Step 8. Scheduling. Only after Step 7 finished cleanly once AND Step 0 showed no other nightly is running:
    training/systemd/install-user-timer.sh --enable
    It sizes MemoryMax and CPUQuota for this machine and checks the unit. Runs 03:30, once a night.
    If a tmux loop already runs the STEM nightly, replace it with the timer instead of running both.

  Step 9. Morning check.
    systemctl --user list-timers | grep aoep-spark
    systemctl --user status aoep-spark-train.service --no-pager | head -12
    tail -40 output/spark/logs/$(ls -t output/spark/logs | head -1)
    cat output/spark/bakeoff/result.json | head -30
    free -g | head -2 ; ps -eo pid,stat,cmd | awk '$2 ~ /Z/ || /spark_nightly|run_finetune|evaluate.py/'
    Expect no leftover training or zombie processes after the cycle ends.

  ROLLBACK
    Stop tonight's runs:   systemctl --user disable --now aoep-spark-train.timer
    Stop a running cycle:  systemctl --user stop aoep-spark-train.service   (kills the whole group)
    Un-promote:            .venv/bin/python -c "import sys; sys.path.insert(0,'training'); from champion import ChampionRegistry as C; print(C('output/spark/champion.json').revert())"
    Restore the 35B server: sudo snap start qwen3-6
    Nothing here changes production; the served model only changes in a separate step.

WHY THE LOOP IS FLAT, AND WHAT TO DO ABOUT IT (measured on the Spark, briefing of 2026-10-24)
  The frozen exam sits at 20.4% for the adapter against 19.9% for the base (target 70%), the same on every
  nightly cycle since 2026-10-23. Each cycle fine-tunes the SAME 373 examples for ONE epoch, so it
  produces essentially the same adapter every night. More cycles on this data change nothing; more compute
  does not help. The bottleneck is training data, not GPU time. Weakest subjects: Health & Wellness 10.2%
  (frozen), calculus 1 11.2% (STEM frozen), python files 12.9% and linear algebra under the floor (split).
  Growth path (data, in order of value):
    1. Authored sessions for the subjects under the 40% floor (the report names them).
    2. Staff-reviewed corrections from the review lab (gold pairs), which are human-checked.
    3. Consented, anonymised class sessions (consent gate is mandatory; no consent means excluded).
  Build and inspect it, without training:
    python3 training/build_train_set.py --report-only
    python3 training/build_train_set.py --out output/spark/data/sessions.grown.json
  The manifest and report list counts per subject and language and mark every subject under the floor.
  Keep a new adapter only when the frozen score rises and every subject is at least 40% (the gate above).

PROMOTION
  training/promote.py moves the champion pointer only when the candidate wins the
  fairness- and behaviour-gated bake-off. Serving a promoted model in production is a
  separate step (an inference node; the LLM deployment is scaled to 0 today).

COSYVOICE (SEPARATE PROJECT, NOT PART OF THIS RUN)
  CosyVoice is at 0 replicas because its manifest needs a GPU node labelled
  aoep.gpu/pool=true and the GPU pool is at 0 - nobody disabled it. Running it in
  production means renting a GPU node (a recurring cost to decide). Improving the
  voice is also different data (reference audio per language and speaker, not
  transcripts). Compare TTS candidates on the same Khmer/Vietnamese/Thai/Spanish/English
  sentences (ASR round-trip error plus a listening panel) before fine-tuning any of them.
  The data on the Spark under output/cosyvoice_* is third-party YouTube audio: confirm the
  licence or consent before any voice built from it ships.
