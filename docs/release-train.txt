RELEASE TRAIN: SCHEDULED MERGE, DEPLOY, RELEASE, AND MOBILE BUILDS
===================================================================
Plain text on purpose (repo no-markdown house rule).

WHY IT EXISTS
  Pull requests arrive from several sources at once (people, parallel workers, Cursor agents) and every one bumps the
  version, so they collide. Two real incidents shaped the design:
    - In zsh an unbraced "$d:latest" expands as "${d:l}atest". Images were pushed to repositories named like
      "course-studioatest" while the cluster kept restarting the OLD images, and the work was reported as deployed.
    - "gh pr merge" run from the wrong directory failed silently and the PR was assumed merged.
  The train never assumes: a merge is proven (state MERGED and the merge commit is an ancestor of origin/main), and a
  deploy is proven (registry digest changed, image label carries the commit, every pod runs the pushed digest).

THE PIECES
  scripts/merge_train.py          decide + merge + trigger deploys (DRY RUN unless --apply)
  scripts/deploy_service.sh       deploy ONE component with proof, rollback and a lock
  scripts/train/components.conf   path prefixes -> Dockerfile, deployment, smoke URLs
  scripts/train/allowlist.txt     author logins allowed to auto-merge without the label
  scripts/train/run_train.sh      one scheduled pass (window, logging, caffeinate)
  scripts/train/*.plist, *.service, *.timer   launchd / systemd schedules
  scripts/mobile_release.sh       native Android/iOS builds, publish, staleness
  scripts/mobile_release.py       parity, staleness, manifest, pruning helpers
  logic and tests: packages/shared/src/aoep_shared/merge_train.py, mobile_release.py and their tests

WHEN A PR MAY MERGE (all must hold)
  1. It has the 'automerge' label (or its author is in scripts/train/allowlist.txt). Every PR in this repo comes from one
     GitHub login, so prefer labelling PRs one by one over allowlisting that login.
  2. GitHub says mergeable and clean. Checks must not be failing or pending. This repo has no CI, so "no checks" is
     accepted; the pre-push hooks and the local checks below are the gate.
  3. Its version bump passes scripts/check_pr_version_bump.sh and the area-scoped tests pass in a throwaway worktree.
  4. It touches no protected path, unless it also has the 'human-approved' label. Protected: infra/, .cursor/rules/,
     .github/, services/identity/, services/billing/, billing and login pages, deploy and train scripts, the
     LICENSE_ALLOWLIST / harvest sources file, the training promotion gate, anything with "secret", "migration",
     "credential" or ".env" in its path.
  A PR that fails 1 is skipped (and counted in the summary). One that fails 4 is labelled needs-human, never merged.

VERSION COLLISIONS
  When a PR is behind main or conflicts, the train rebases it in a temp worktree. Only mechanical conflicts are
  resolved: VERSION, build-info.txt, the two version.ts files, the package.json / app.json / pyproject version, and the
  top of CHANGELOG.txt (both sides' entries are kept, newest first). It then runs scripts/bump_pr_version.py.
  Any other conflict aborts the rebase and the PR is labelled needs-human.
  It NEVER force-pushes. The rebased work goes to a NEW branch train/<branch>-rN and a superseding PR is opened; the
  original PR and branch (including cursor/* branches) are left untouched, for the owner to close.

ONE AT A TIME
  Per run: at most --max-merges PRs (default 1), then the changed paths decide which components deploy, in a safe order
  (backends first, web last), one rollout at a time. A deploy lock stops two deploys overlapping.

DEPLOY PROOF (scripts/deploy_service.sh)
  1. lock, PAUSE check, commit must be HEAD, clean, and on origin/main.
  2. capacity gate (scripts/node_analyzer.py): refuses when fewer than 3 nodes are healthy, any node is not ready, or
     CPU or memory requests are above 90%. Only a few nodes are usable today, so a rollout needs headroom.
  3. build with explicit braced tags (:latest and :<sha12>) and an image revision label, then push.
  4. the registry digest of :latest must differ from before. The image config must contain the commit sha.
  5. rollout restart + status; every running pod's imageID must end with the pushed digest.
  6. smoke: each URL in components.conf must be 2xx/3xx, and 10 hits of the first URL must show no 5xx.
  7. on success: record the deployment on GitHub with the real sha, then publish the release.
  8. on ANY failure after the push: re-point :latest at the previous digest (kubectl rollout undo cannot help with a
     mutable :latest tag), restart, wait, record a FAILED deployment. The train then writes scripts/train/PAUSE itself
     so nothing else merges or deploys until a person looks.
  Manual use:  scripts/deploy_service.sh web --dry-run     then     scripts/deploy_service.sh web
  The older scripts/post_deploy_smoke.sh expects digest-pinned or sha-tagged deployments; these deployments use
  :latest, which is why the smoke here is in the script itself.

KILL SWITCH, LOCK, LOGS
  touch scripts/train/PAUSE          nothing merges or deploys (the dry-run summary still works)
  rm scripts/train/PAUSE             resume
  output/train/train.lock            one train at a time (stale locks from dead processes are replaced)
  output/train/train-YYYYMMDD.jsonl  structured events: merged, merge_failed, deploy
  output/train/latest-summary.txt    what merged, what is stuck and why, what is ready, mobile staleness
  output/train/run.log               the scheduled passes

SCHEDULING (honest limits)
  A scheduled job on a laptop only runs while the laptop is awake.
  Mac:    sed "s#__REPO__#$PWD#g; s#__HOME__#$HOME#g" scripts/train/com.salareen.merge-train.plist \
            > ~/Library/LaunchAgents/com.salareen.merge-train.plist
          launchctl load ~/Library/LaunchAgents/com.salareen.merge-train.plist
          Every 15 minutes, dry run first. Change TRAIN_APPLY to 1 in the plist once the summaries look right.
          run_train.sh wraps each pass in caffeinate so the Mac cannot sleep mid-deploy. To wake it for the window:
          sudo pmset repeat wakeorpoweron MTWRFSU 07:55:00
  Linux:  copy merge-train.service and merge-train.timer to ~/.config/systemd/user, then
          systemctl --user daemon-reload && systemctl --user enable --now merge-train.timer
  TRAIN_WINDOW=08-23 limits real merges to those local hours; outside it a pass is a dry run.
  The deploy step needs on the machine that runs it: gh (logged in), docker with push access to sjc.vultrcr.com,
  kubectl with the cluster context, and VULTR_REGISTRY_USERNAME / VULTR_REGISTRY_PASSWORD already logged in.
  Nothing here stores or reads secrets.

MOBILE (native builds only; no EAS, no OTA)
  Policy: .cursor/rules/no-eas-build-mobile.mdc. The JS bundle is embedded in every native build, so every change under
  apps/mobile/src ships only with a new build. Web pages inside WebViews (demos, labs) update with each web deploy.
  Check:    python3 scripts/mobile_release.py staleness        (also in the train summary)
            Today the downloadable Android app is v0.94.9, many versions behind main.
  Parity:   python3 scripts/mobile_release.py parity           (VERSION, package.json, app.json, src/version.ts)
  Android:  scripts/mobile_release.sh --android --publish [--prune]
            builds with the existing Gradle script, verifies the embedded bundle, checks the signature (rejects the debug
            key), uploads the APK to Vultr Object Storage with the aws CLI, then uploads releases/android/latest.json.
            The web route /download/android reads that manifest (60 second cache), so publishing it IS the update: no web
            redeploy. The manifest URL host is allow-listed, so a bad manifest cannot become an open redirect.
            One-time setup: an aws CLI profile with the Object Storage keys (your own config; the script never reads it).
  iOS:      scripts/mobile_release.sh --ios
            builds the .xcarchive with xcodebuild. Upload is automatic only if you create an App Store Connect API key
            (App Store Connect > Users and Access > Integrations), export ASC_KEY_ID and ASC_ISSUER_ID and save the .p8 as
            ~/.appstoreconnect/private_keys/AuthKey_<ASC_KEY_ID>.p8, and commit apps/mobile/ios/ExportOptions.plist.
            Otherwise it stops with exit 10 and prints the Xcode Organizer steps (Distribute App > App Store Connect >
            Upload, then TestFlight).
  In-app prompt: the app calls GET https://www.salareen.com/app-version at most once a day and shows a small mascot
            "A new Salareen is ready" card with Update now / Not now. A build below min_supported (set it in the Android
            manifest, or IOS_MIN_SUPPORTED for iOS) cannot dismiss the card. iOS needs IOS_LATEST_VERSION and
            IOS_STORE_URL set on the web deployment because TestFlight links are not files we host.
  A fleet-status line for mobile staleness was not added to scripts/fleet_status.sh to avoid conflicts with the fleet
  tooling; the same line is in the train summary.

COMMANDS
  python3 scripts/merge_train.py                       what would happen (safe)
  python3 scripts/merge_train.py --apply               merge one eligible PR and deploy what it changed
  python3 scripts/merge_train.py --pr 777 --apply      only that PR
  gh pr edit 777 --add-label automerge                 opt a PR in
  gh pr edit 777 --add-label human-approved            allow a protected-path PR through
  touch scripts/train/PAUSE                            stop everything
